02 — ANALYTICAL CONTEXT & OBJECTIVE

Use SQL queries to understand where sales come from and how products perform.

The project establishes a compact sales dataset in Microsoft SQL Server and applies grouped calculations to answer practical product, time, category and location questions.

THE ANALYTICAL NEED

Raw transaction rows are difficult to compare directly.

A list of sales records does not immediately show which products move the most units, which products contribute the highest revenue, how revenue changes over time or how sales are distributed across locations and categories.

THE OBJECTIVE

Convert transaction-level data into useful summaries.

Create a sales database and table, populate it with records, then use T-SQL aggregation and date-based grouping to produce ranked and summarized result sets that can be reviewed in SQL Server Management Studio.

03 — DATA & QUERY STRUCTURE

A straightforward single-table SQL analysis design.

This project does not implement a multi-tier application or a multi-table data warehouse. Its structure is intentionally represented as a database setup, one sales table, a set of analytical T-SQL queries and their result sets.

Database layer

The SQL script creates the Sales_Analysis database and selects it as the working database.

Sales table

A single Sales table stores Sales_Id, Sale_Date, Product_Name, Category, Quantity, Price and Location.

Query layer

T-SQL statements use SUM, GROUP BY, ORDER BY, TOP and date functions to calculate sales summaries.

Analysis output

The queries return ranked product lists and revenue summaries by month, quarter, location and category. Results are reviewed in SSMS and documented in the project report.

DATA MODEL NOTE

The implemented schema is one transaction-style table. The case study therefore describes the actual table and query flow rather than suggesting joins, ETL pipelines, dashboards or a star schema that are not present in the SQL script.

04 — ANALYTICAL DESIGN

Organize the analysis around clear business dimensions.

The query set is grouped by the questions it answers. Each analysis uses the relevant columns in the sales table and calculates revenue from quantity multiplied by price.

Product ranking

Compare the top five products by total units sold, then rank products by calculated revenue.

Time-based trends

Group calculated revenue by calendar month and quarter to review how sales value changes across periods.

Location comparison

Aggregate revenue by the Location field to compare the cities represented in the dataset.

Category contribution

Summarize revenue by product category to compare the sales value associated with each category.

CALCULATION BASIS

Revenue = Quantity × Price. The SQL script applies this expression in the product revenue, monthly revenue, quarterly revenue, location and category queries.

06 — ANALYTICAL CAPABILITIES

What the SQL script actually calculates.

The following capabilities are directly represented by the query blocks in Sales_Data_Analysis.sql.

Top products by units

Returns the top five products after summing Quantity and sorting the total units sold in descending order.

Top products by revenue

Calculates SUM(Quantity * Price) for each product and returns the five highest revenue totals.

Monthly revenue

Formats Sale_Date into a year-month value and groups revenue by month in chronological order.

Quarterly revenue

Uses YEAR, DATEPART(QUARTER) and CONCAT to calculate and order quarterly revenue.

Revenue by location

Groups the calculated revenue by city/location and sorts the results from highest to lowest revenue.

Revenue by category

Groups the calculated revenue by product category to compare category-level sales value.

SQL CONCEPTS VISIBLE IN THE SCRIPT

Database and table creation, primary key definition, multi-row inserts, SELECT, TOP, SUM, GROUP BY, ORDER BY, FORMAT, YEAR, DATEPART and CONCAT.

07 — RELIABILITY & PROJECT SCOPE

Keep the calculations transparent and the project claims precise.

The project is a compact SQL analysis exercise. Its strengths and limitations should be understood in the context of the supplied schema, inserted records and query set.

Explicit revenue calculation

Revenue is calculated directly from Quantity * Price in the SQL statements, making the calculation basis visible and reviewable.

Defined table structure

The Sales_Id field is declared as the primary key, while date, product, category, quantity, price and location fields are explicitly typed.

Reproducible SQL artifact

The repository includes the SQL script that creates the database, defines the table, inserts records and executes the analysis queries.

Scope limitations

The current implementation uses one table and a fixed set of inserted records. The repository does not document a live data feed, automated refresh, dashboard deployment, multi-table joins or a production ETL process.

Scope note: This case study presents the SQL Server work and documented project artifacts. It does not claim a production sales system, predictive forecasting, advanced statistical modeling or independently measured business impact.
