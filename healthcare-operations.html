02 — BUSINESS CONTEXT & OBJECTIVE

Bring different hospital functions into a unified analytical view.

Healthcare operations span multiple functions. This project organizes those areas into a connected reporting solution so users can review performance across operational, patient, clinical and financial domains.

THE CHALLENGE

Operational information is distributed across functions.

Hospital capacity, patient activity, emergency services, surgeries, laboratory work, physician performance, pharmacy activity and financial performance represent different aspects of healthcare operations. Reviewing them separately can make it harder to form an overall view of performance.

THE OBJECTIVE

Build a structured, multi-area BI solution.

Develop a Power BI platform with a reusable analytical data model, transformed source data, DAX-based KPIs and nine dashboard modules. The solution is designed to support operational monitoring and comparison across the documented healthcare functions.

03 — ANALYTICAL ARCHITECTURE

Structure healthcare data before turning it into operational reporting.

The repository documents a Power BI solution built around Power Query transformations, a 17-table fact-and-dimension model, DAX measures and published report consumption through Power BI Service.

Source data layer

Microsoft Excel is included in the project technology stack as a source and data-handling tool for the healthcare information used by the report.

Preparation layer

Power Query is used for data cleaning and transformation before the data is shaped for analysis in Power BI.

Analytical model layer

A 17-table model combines healthcare fact and dimension tables covering patients, hospitals, doctors, departments, diseases, treatments, admissions, appointments, emergency services, surgeries, laboratory services, pharmacy transactions and billing.

Reporting & delivery layer

DAX provides business KPIs and analytical measures. Power BI Desktop is used to develop the dashboards, with the completed solution published to Power BI Service and organized as a dedicated Power BI App.

04 — REPORT & ANALYTICS DESIGN

Organize the report around the decisions each healthcare function needs to support.

The nine dashboard modules separate the reporting experience by functional area while retaining a shared analytical foundation.

Executive-level visibility

The Executive Overview provides a consolidated view of overall healthcare performance for high-level monitoring.

Operational and patient context

Hospital Operations and Patient Analytics focus on capacity, operational metrics, patient demographics and utilization.

Clinical service monitoring

Emergency, Surgery, Laboratory and Physician Performance modules provide focused views of service activity, outcomes, testing and workload.

Medication and financial views

Pharmacy Analytics covers pharmacy activity and medicine utilization, while Financial Performance addresses revenue, insurance, patient contribution and discounts.

DESIGN PRINCIPLE

Keep each dashboard focused on a defined healthcare function, while using a common analytical model and consistent KPI logic across the solution.

07 — MODEL & DELIVERY CONSIDERATIONS

Make the analytical foundation and project scope clear.

A BI solution should communicate how its reporting is organized and what its published artifacts demonstrate.

Structured analytical model

The repository documents a 17-table fact-and-dimension model spanning the healthcare entities and transaction areas used by the solution.

Reusable KPI logic

DAX-based business KPIs and analytical measures support reporting, including time-based and year-over-year analysis, KPI comparisons and conditional formatting.

Interactive report experience

The documented solution includes interactive slicers and cross-filtering to support exploration across dashboard content.

Published delivery

The project README records that the completed solution was published to Power BI Service and organized as a dedicated Power BI App.

Scope note: This is a completed portfolio BI project. The repository does not document independently measured hospital outcomes, production integration with a live hospital information system, or use for clinical decision-making. The case study therefore makes no claims about real-world patient impact.
